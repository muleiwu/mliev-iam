# 遗留事项调研 · P3 — 应用侧资料写回与同步（架构演进）

> 影响等级：**P3（架构演进，有真实需求再做）**
> 调研日期：2026-07-15
> 背景：IAM 作为用户资料权威源，个人中心已让用户在 IAM 内改资料。下一步让业务应用能读到最新资料、必要时写回。

三条技术路线：①应用侧资料写回（scope 控制的 Profile Write API）②SCIM 2.0 ③资料变更 webhook。

## 0. 地基确认（决定三条路线成本）

### 0.1 OIDC Access Token 的真实形态
IAM 的 access token 是**「签名 JWT + DB 落库」的混合体**：
- 授权码/刷新流程签发 **RS256/HS256 JWT**（`oidc_id_token_service.go:200-229 GenerateAccessToken`，用应用主密钥签名）。
- **同一 token 字符串同时写入 `oidc_tokens` 表**（存 SHA256 hash，`oidc_authorization_service.go:575-603`）。
- **userinfo 校验走 DB 查表，不验 JWT 签名**：`OIDCUserInfoService.GetUserInfo` → `tokenDAO.GetValidByAccessToken(token)`（`oidc_userinfo_service.go:34-53`），DAO 把 token SHA256 后查 `access_token_hash`，过滤 `is_revoked=false AND expires_at>now`（`oidc_token_dao.go:49-58`）。
- **scope 存在每条 token 记录上**：`OIDCToken.Scopes []string`（`oidc_token.go:34`），附 `HasScope()`（`:122`）。

> 结论：路线一「用 access token 写资料」可完全复用 `GetValidByAccessToken` + `token.Scopes` + `token.UserID`，无需引入 JWT 验签，成本很低。

### 0.2 client_credentials 机器令牌
`ExchangeClientCredentials` 生成 JWT 并写入 `oidc_tokens` 表，`user_id=0`、无用户会话；不生成刷新令牌，数据库中的 `refresh_token` 为 `NULL`。未来 SCIM 若使用此令牌，可复用 `GetValidByAccessToken` 验证有效期与撤销状态，但仍需独立校验客户端、作用域和接口权限。

## 路线一：应用侧资料写回（scope 控制的 Profile Write API）

### 现有 scope 机制
- 解析 `ParseScopes(scopeStr)`（`oidc_authorization_service.go:864`）内部只做 `strings.Split(scopeStr, " ")`。
- **无 scope 值白名单校验**：请求什么 scope 就带什么，仅 discovery 静态声明支持集（`oidc_userinfo_service.go:212`）。
- 刷新时 scope 只能收窄（`validateRefreshScopes:547-561`）。
- scope → 字段映射（只读消费）：`BuildUserInfoResponse`（`oidc_userinfo_service.go:57-149`）按 `hasScope` 返回 profile/email/phone/address 字段。

### userinfo 端点：只读确认
- `GET/POST /oidc/:client_id/userinfo` → `OIDCController.UserInfo`，强制 `openid` scope。
- 返回 sub/name/nickname/preferred_username/picture/email/phone/address 等。
- **完全只读**，无 PUT/PATCH。

### 写资料接口需要什么
- **内部已有写能力但走内部 JWT**：`PUT /api/user/profile` → `UserController.UpdateUserProfile` → `UserService.UpdateMyProfile`（`user_service.go:312`，白名单只允许 `Nickname/RealName/Avatar/Remark`）。
- **中间件缺口**：`AuthMiddleware`（`auth_middleware.go:94`）只认内部 JWT（`admin_access_token`/`user_access_token` Cookie 或 Bearer），**不认 OIDC access token**。→ Profile Write API 必须新增中间件。
- **字段分级（现成分层可沿用）**：自助可写 `Nickname/RealName/Avatar/Remark`；必须走验证 `email/phone`；管理员专属 `status/isActivated/emailVerified/phoneVerified`；自由扩展 `user.Attributes`。

### 落地骨架
```
1. 新 scope 常量 profile:write（ParseScopes 自动透传；建议在 oidc_userinfo_service.go:212 ScopesSupported 补声明）
2. 新中间件 app/middleware/oidc_token_middleware.go：
   extractAccessToken → dao.GetValidByAccessToken(tok) → 校验 token.HasScope("profile:write") → c.Set("user_id", token.UserID)
   （100% 复用 0.1 的现成校验链）
3. 新路由 PUT /oidc/:client_id/profile（或 /api/oidc/profile），handler 复用 UserService.UpdateMyProfile
   （email/phone 走单独验证发码流程 SendVerificationCode）
4. （可选）Application.OIDCProtocolConfig.Scopes 增加"哪些应用可申请 profile:write"的白名单校验
```
**成本：小（1-2 天）**。零新表，复用 token 校验 + UpdateMyProfile + 字段白名单。

### 术语陷阱
`Application.AccessScope` **不是 OAuth scope**，是"哪些用户可访问该应用"的访问控制（`application.go:106-163`，接口 `GET/PUT /admin/applications/:id/access-scope`）。真正的 OAuth scope 在 `OIDCProtocolConfig.Scopes`（`application.go:62`）。设计勿混淆。

## 路线二：SCIM 2.0

### 现有痕迹：零实现
全仓 `.go` 无 SCIM 代码，仅文档 `_docs/ENTERPRISE_IDENTITY_PROVIDER_INTEGRATION_ASSESSMENT.md` 列为长期能力。属从零实现。

### 方向：现有 identity provider 是入站，SCIM 是出站补充
钉钉/飞书/企微适配器（`app/service/protocol/identity/*`）接口只有 `GetAuthURL/ExchangeToken/GetUserInfo`——纯入站 SSO 登录 + 拉取信息，无 provisioning。SCIM 是相反方向（HR/企微/钉钉作为 client 把变更推入 IAM，或 IAM 出站推给下游），两者互补。

### User 模型 → SCIM User schema 映射（现成字段基本够用）
| SCIM attr | IAM 字段 |
|---|---|
| id | UUID |
| userName | Username |
| name.formatted | RealName |
| displayName | Nickname |
| emails[] | Email + EmailVerifiedAt |
| phoneNumbers[] | Phone + PhoneVerifiedAt |
| photos[] | Avatar |
| active | Status/IsActivated |
| meta.created/lastModified | CreatedAt/UpdatedAt |
| enterprise ext | Attributes JSONObject |
| groups | user_departments / user_roles 关联表 |

CRUD 底座已有：`UserService.CreateUser/UpdateUser/GetUserList/DeleteUser/UpdateUserStatus` + 完整 `UserDao`。SCIM 层主要做 **schema 转换 + 协议封装（filter/分页/PATCH ops/错误格式）**。

### 认证
`client_credentials` 令牌已落库（0.2）；SCIM 可复用现有令牌查询，仍需实现客户端身份、`scim` scope 与接口权限校验。

**成本：中-大（1.5-3 周）**。需新建 `/scim/v2/Users`（list+filter/get/post/put/patch/delete）、`/Groups`（可选）、`/ServiceProviderConfig`、`/Schemas`、`/ResourceTypes`；schema 转换层；PATCH op 解析；SCIM 错误格式；验证中间件。User CRUD 底座可复用，纯协议壳工作量大。

## 路线三：资料变更事件 webhook

### 现有事件基础设施：几乎没有
- 无 event bus / hook 框架 / 消息队列 / 定时任务 / 异步 job 框架。
- 唯一"webhook"是入站 OIDC 同意回调（`POST /webhook/oidc/consent`），与出站事件无关。
- 唯一异步先例：数据迁移用裸 `go func()`（`migration_import_service.go:123,137`，无 worker pool / 重试 / 持久化队列）。

→ webhook 需从零搭：事件产生点 + 投递器（HTTP + 签名 + 重试 + 死信）+ 订阅配置存储。

### 设计要点
- `Application.ProtocolConfig` JSON 可直接塞 `callbackUrl/webhookSecret/events[]`（零迁移），或新建 `application_webhooks` 表更规范。
- 事件产生点 hook 进写路径：`UserService.UpdateUser` / `UpdateMyProfile` / `UpdateUserStatus` 之后发 `user.updated`。
- 签名 HMAC-SHA256（仓库已有 `crypto/sha256` 用法）。
- 重试需自建（`go func()` + 指数退避 + 落库重试记录，或引入 asynq 等轻量队列）。

### 与"登录/刷新时重取 userinfo"最轻方案的对比（已确认）
**现在应用重新登录 / 刷新 token 时确实会拿到最新资料，零后端改动即可实现弱同步**：
- userinfo 每次从 DB 实时读（`GetUserInfo` → `GetUserModelByID`）。
- 刷新 token 时重建 id_token：`RefreshToken` → `GenerateTokens`，`hasScope openid` 时 `GetUserModelByID` 重取用户并重建 id_token。
- 授权码换 token 同理，每次登录 id_token/userinfo 都是最新。

→ **应用在 token 刷新周期（access 1h / refresh 30 天）内重新调 userinfo 或刷新 token 即可获得最新资料，这是零后端成本的默认能力**。webhook 只在需秒级实时推送时才有增量价值。

**成本：中（1-2 周可靠版）**，或 **0（用刷新 userinfo 弱同步）**。

## 通用：加新表/新字段

迁移用 **goose 版本化 SQL**（非 AutoMigrate），embed 打包，安装时触发。**三方言各一份**：`migrations/{mysql,postgresql,sqlite}/`，文件名 `YYYYMMDDHHMMSS_name.sql`，含 `-- +goose Up/Down`。
步骤：定义 GORM model → 三方言各写同版本号迁移 SQL → 新建 DAO（参照 `oidc_token_dao.go`）。JSON 列用 `gorm:"type:json;serializer:json"`。加字段可直接 `ALTER TABLE ADD COLUMN`（runner 有字段漂移修复逻辑）。

## 推荐优先级与骨架

**路线一 > 路线三(弱同步) > 路线二 > 路线三(webhook 可靠版)**

| 路线 | 成本 | 复用度 | 建议 |
|---|---|---|---|
| 一 Profile Write API | 小（1-2 天） | 极高 | **首选**。只缺 1 中间件 + 1 路由 + 1 handler |
| 三 弱同步（刷新 userinfo） | 0 | 已是默认行为 | **立即可用**，写文档告知接入方即可 |
| 二 SCIM 2.0 | 中-大（1.5-3 周） | 中（CRUD 底座可复用） | 等 HR/企微双向 provisioning 明确需求再做 |
| 三 webhook 可靠版 | 中（1-2 周） | 低（无任何事件/队列基建） | 仅需秒级实时推送时做 |

### 路线一最小骨架（推荐先做）
```
1. app/middleware/oidc_token_middleware.go
   extractAccessToken(c)                        // 复用 oidc_controller.go:204
   dao.NewOIDCTokenDAO(db).GetValidByAccessToken(tok)  // oidc_token_dao.go:49
   require token.HasScope("profile:write")      // oidc_token.go:122
   c.Set("user_id", token.UserID)
2. router: oidc.PUT("/:client_id/profile", ...)（挂上述中间件）
3. handler: 复用 UserService.UpdateMyProfile(userID, req)  // user_service.go:312
4. oidc_userinfo_service.go:212 ScopesSupported 补 "profile:write"
5. （可选）应用白名单校验 profile:write
```
零新表、零迁移。

## 需要注意的坑
1. `Application.AccessScope` ≠ OAuth scope（前者是用户访问控制）；OAuth scope 在 `ProtocolConfig.Scopes`。
2. `AuthMiddleware` 不认 OIDC access token，路线一必须新中间件。
3. client_credentials token 落 `oidc_tokens` 表且无用户身份，SCIM 若用它认证仍需独立校验客户端和 `scim` scope。
4. 系统无 scope 值校验（`ParseScopes` 只 split），若 `profile:write` 要限授权应用需自建校验。
5. 迁移必须三方言各写一份，否则 sqlite/postgres 部署缺表。
